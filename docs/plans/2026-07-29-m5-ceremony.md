# M5 — the ceremony (PR-D)

Advances `truth_cutover_generation` from 0 to 1, turning the truth-exposure
contract on for the first time. PR-B (#408, `f29c2c54`) shipped the substrate;
PR-C (#409, `3932e3d5`) shipped the adapters. Neither enforces anything: at
generation 0 `page_visibility` answers `Full` for every page, so every adapter
is the identity function.

Advancing is **destructive**. The projection pass deletes the `.md` of every
page the contract hides, out of the user's real vault. Everything below exists
so that deletion cannot outrun the read gates.

## Decisions taken 2026-07-29

Four forks were put to the user with evidence; all four took the recommended
option.

| # | Decision | Chosen |
|---|---|---|
| 1 | How to close `/api/activities` | **Redact at read time** |
| 2 | `GET /api/memory/entities/{id}` | **Demote — it is mislabeled** |
| 3 | How much ceremony debt lands before the flip | **Minimum-safe** |
| 4 | How an operator advances the generation | **CLI with mandatory dry-run** |

### 1 — `/api/activities`: redact at read time

The title is baked into the free-text `detail` column at **write** time by four
sites (`post_write.rs:2078`, `:2163`, `:2918`, `post_ingest.rs:356`), and
`agent_activity` (`db.rs:3992-4000`: `id, timestamp, agent_name, action,
memory_ids, query, detail`) has no page reference at all — `memory_ids` holds
memory ids. So a write-path fix leaves every existing row leaking, and there is
nothing to key a per-page filter on.

Chosen fix: when the resolved grant is not `Full`, blank `detail` on any
`page_*` action. This is **fail-closed without identifying the page** — the
route does not need to know *which* page a row names in order to refuse to
show the sentence. It covers historical rows the moment it ships, needs no
migration, and destroys nothing.

Rejected: adding a `page_id` column plus a migration that nulls historical
`detail` (schema change, and the migration permanently destroys existing
activity text); and demoting the route (a deliberate hole).

### 2 — `GET /api/memory/entities/{id}`: demote

The manifest justifies page-bearing with `"Entity.name = pages.title (M3)"`
(`truth_manifest.rs:199`). The evidence says that is a conflation:

- The field reads from `pages` only when the per-consumer
  `entity_reader_cutover` for `"scoped_entities"` is on
  (`db/scoped_entities.rs:99-131`, gated by `reader_uses_entity_pages`,
  `db.rs:17648-17701`). It is **default OFF**, so in production the field is
  plain `entities.name` and no `pages` row is touched.
- Even with the cutover on, `pages.title` for a `kind='entity'` shadow is a
  byte-for-byte mirror of `entities.name`, kept in sync at write time by
  `update_entity_shadow_page` (`db.rs:9945-9968`), not independently authored
  page prose.
- Observations and relations come from `observations` / `relations`, never
  `pages` (`db/scoped_entities.rs:146-180`).
- Real page readers already exclude `kind='entity'` shadows (`db.rs:89481`).

So the route exposes the entity's own name, duplicated into a shadow row for an
unrelated migration. **Re-verify this trace inside the PR before committing the
demotion** — a demotion is a security-relevant edit and secondhand evidence is
not enough to land one.

### 3 — Minimum-safe scope

Build before the flip:

- **The write fence.** Pages are projected at runtime (`post_write.rs:2852`),
  so without a fence a page written mid-ceremony slips past the pass that just
  ran. Fully specified at `docs/plans/2026-07-27-m5-migration-state-machine.md:20-273`
  (`(epoch, phase)`, cutover lease); no code exists — `set_truth_cutover_generation`
  (`db/truth_exposure.rs:280-283`) is a bare `set_app_metadata` write with no
  fence or CAS.
- **The export permit.** Export writes prose to disk outside the HTTP gate and
  currently hardcodes its grant: `export/knowledge.rs:520` passes
  `TruthGrant::Automatic` directly. No `TruthPermit` type exists anywhere.

Demote rather than build:

- **Page-map** (`GET /api/pages/{id}/map`) drops to `MarkerShape::None` so it
  refuses rather than half-serves. `handle_get_page_map`
  (`page_map_routes.rs:190-214`) returns raw nodes/edges with zero visibility
  filtering today, and hiding a node in a graph is a design problem — incident
  edges are keyed by node ids, not page ids — with no design yet.

Defer:

- **Typed `AdapterId` / `TruthResponse<T>`** with a private constructor. Today
  `adapter` is `&'static str` on all three reader structs (`truth_manifest.rs:111`,
  `:124`, `:134`), so a missing adapter is a runtime string, not a compile
  error. Real ergonomics win, not a safety gate for this flip.

### 4 — `wenlan truth cutover`, dry-run mandatory

Nothing in production reaches `set_truth_cutover_generation` today: every
caller is a test (`db/truth_exposure_test.rs`, `export/projection_invariant_test.rs`),
and no route, CLI command, migration, or startup path touches it. An ordinary
upgrade therefore cannot advance the generation — but the ceremony has to build
the surface that does.

`wenlan truth cutover --dry-run` lists every page that would be hidden and every
`.md` that would be deleted from the vault. `--apply` refuses unless a dry-run
has been produced for the same state. Rejected: an HTTP admin route, which would
make a vault-deleting operation reachable by anything that can reach :7878,
including agents.

## Stages

1. **Done** (`e5a99764`). Re-verify the entity-route trace, then demote it and
   page-map in the manifest; fix the counts and the manifest tests.
2. **Done** (`7508d6cc`). `/api/activities` read-time redaction + a tooth that
   fails if a `page_*` row's `detail` survives.
3. **Done.** The write fence, per the state-machine spec.
4. **Done.** A permit consumed before every production page-prose write.
5. **Done.** The cutover command with the dry-run gate.
6. The flip itself, behind all of the above. **Blocked — see "What blocks the
   flip" below. Two things must land first, and neither was in the original
   plan.**

### What stage 3 built

`(epoch, phase)` in `app_metadata` under `truth_cutover_fence`, swapped by a
single conditional SQL statement rather than a read-then-write. `begin_cutover`
mints a `CutoverLease` (private field, so it cannot be fabricated);
`commit_cutover` writes the generation and *then* releases the fence, which is
the §7.5 ordering invariant; `abort_cutover` returns to `off` **at a new epoch**,
which is what makes the ABA test pass.

`page_write_permit` is where writers feel it: while a ceremony prepares, every
page write is refused. An unreadable fence propagates as an error rather than
defaulting — "inert" for a fence means letting writers through, and that is
exactly wrong when the ceremony state is indeterminate.

The PR-B tooth `the_cutover_setter_has_no_production_caller` is amended, not
deleted, exactly as its own failure message instructed: it now allows the single
call in `commit_cutover` and fails on a second one in the same file.

### What stage 4 found

The plan above assumed export was the gap. The real gap was narrower and worse:
**`enforce_projection_directory_invariant` has exactly one production caller,
at daemon startup** (`wenlan-server/src/main.rs`). There is no sweep behind an
ungated write, so a page re-projected past the permit sits in the user's vault
until the next restart.

Two production paths did exactly that:

- `post_write.rs` `regenerate_page_projection_cas` — the receipted lint/repair
  operation. Now takes the permit **before** the connection mutex (the closure
  below it holds that mutex, and the permit needs the same connection) and
  **refuses** without one: telling a caller "repaired" while the file was never
  rewritten is worse than an error.
- `sources/page_watcher.rs` — re-projects from DB truth when a user's edit
  touched the protected Sources block. Now **skips** without a permit, which is
  the honest response for an ambient reaction to a file the user touched.

The projection invariant's own hardcoded `TruthGrant::Automatic`
(`export/knowledge.rs`) is correct and stays: the reader there is a filesystem,
which declares no contract and carries no human gesture.

## Not in this PR

- Typed `AdapterId` / `TruthResponse<T>` (deferred above).
- Page-map hiding as a graph transformation (demoted above; needs a design).
- Rewriting the four `detail` write sites to carry a page reference — the
  read-time redaction makes it unnecessary for safety, and it stays available
  later if the activity log should keep showing titles to permitted readers.

### What stage 5 built, and a tooth that had to be rewritten

`wenlan-server truth-cutover [--generation N] [--apply]` — a hidden maintenance
subcommand on the daemon binary, mirroring `backfill-stale-pages`: refuses while
the service is registered or a daemon answers, takes the data-root lock, opens
the DB directly.

Decision 4 said "CLI, not an HTTP admin route". This is stricter than the CLI
would have been: the `wenlan` CLI talks HTTP, so putting it there would have
needed exactly the route the decision rejected. On the daemon binary it is
reachable only from a shell on the machine, and only with the daemon stopped.

The ordering lives in `KnowledgeWriter::run_truth_cutover`, not in the command,
so it is testable in core: take the lease → evict the files → commit the
generation → release the fence → reconcile.

**Two teeth shipped in the first draft did not hold, and were rewritten.** Both
passed under the mutation they were supposed to catch:

- The happy-path ceremony test could not tell directory-first from commit-first,
  because the reconcile pass afterwards deletes the same files either way. The
  ordering is only observable when the directory work *fails*, so the
  replacement forces that (read-only projection root, unix-only) and asserts the
  generation still reads 0 — a committed generation with the prose still on disk
  is the exact "false trust" state directory-first exists to prevent.
- The digest test changed the eviction list along with the projection, so a
  digest over the eviction list alone would still have caught it. The
  replacement adds a *supported* page between plan and apply, which leaves the
  eviction list byte-identical and moves only the digest.

## What blocked the flip, and what was done about it

Two findings, neither in the plan above, both inert at generation 0 and both
live the moment the generation advances. Stage 6 was going to be the flip; it
became these four fixes instead, after the user read the design and rejected its
premise. All four are in PR-D.

### 1. The flip would have emptied the vault

`page_truth_state.support_status` is written in exactly one production place:
the migration backfill `backfill_page_truth_state` (`db/claim_identity.rs`),
which stamps **every** page `'provisional'` with the reason `"never evaluated:
predates claim derivation"`. Every other write in the workspace is in a test
file.

`visible_at` hid any page that was not `supported`. Advancing to generation 1
would therefore not have evicted the unsupported pages — it would have evicted
**all** of them: 511 `.md` files on the author's own machine.

Worse, the rule that looked most fail-closed was the real outage. The old
contract read "no `page_truth_state` row" as unsupported, on the principle that
absence of a support record is not evidence of support. But `insert_page` never
creates a row — the backfill is the only writer — so *every page created after
migration 99 has no row, forever*. That rule did not fail closed on a rare gap;
it hid one hundred percent of future pages the instant the generation advanced,
and hid them silently, since nothing would ever arrive to un-hide them. A
fail-closed case that is *every* case is not a safety property.

**Fixed** by giving support three states instead of two. `Support::Unevaluated`
is not a verdict and is never treated as one: an unjudged page keeps full
visibility at every generation. Only `Support::Unsupported` — judged, and the
evidence did not back the prose — costs a page its place in the projection. The
two are told apart by `page_truth_state.evaluated_at`, added in migration 103
and left NULL by the backfill, which is what makes flip day move zero of 511
pages.

`human_reviewed` was the second half of the same bug. The column has existed
since migration 98, was read into `PageTruth`, carried as far as
`truth_adapter.rs`, and then dropped on the floor — no visibility or eviction
path consulted it. A page its owner had personally approved was treated exactly
like one nobody had ever seen. It now outranks the machine judgment, which is
the only ordering that makes sense: a person approving a specific page version
against a specific digest is a stronger signal than a model's read of the
citations.

### 2. Eviction missed duplicate files for the same page

`scan_projected_page_ids` returned `HashMap<page_id, filename>` — one filename
per page. `wenlan pages` reads *every* top-level `.md` in the directory
(`wenlan-cli/src/commands/pages.rs` `read_pages`). So if two files carried the
same `origin_id` — a sync-conflict copy from Obsidian Sync, iCloud, or Dropbox
is the ordinary way this happens — eviction removed one and the reader still
found the other.

Found by the cross-model review. **Fixed** by returning every filename per page
and moving all of them. The three call sites collapsed into one helper,
`projected_files`, which is now the single place the union of `state.json` and
the directory scan is computed — the old code did that union twice, differently.

### 3. Eviction deleted the file

The original design unlinked the `.md`. The user's objection: `knowledge_path`
is very often their own vault, they may have edited the prose by hand, and
hiding a page is a retrieval decision — it says the prose is not backed by its
evidence — not a licence to destroy it. The database can rebuild a page; it
cannot rebuild what a person typed into the projection.

**Fixed** by moving the file to `<knowledge_path>/archive/` instead. Plain and
visible, not a dotfile: someone looking for a page that disappeared should find
it without being told where to look. It works as enforcement because
`wenlan pages` reads one directory level of `*.md`, so an archived page leaves
Wenlan's own reader — the surface the M5 manifest names — while staying
somewhere a human can reach. It also stays out of `scan_projected_page_ids` for
free, since a directory has no `.md` extension, so an archived page is not
rediscovered and re-archived on the next pass.

Naming: **archive**, not "withdrawn". The user's call, and the better word — it
says where the file went rather than passing judgment on it.

### Still not built: the promotion path

The claim-derivation path that marks a page `supported` still does not exist.
That is no longer a blocker for the flip, because unjudged is now safe. It is a
blocker for the flip doing anything at all: until something judges pages, the
cutover is a no-op by construction. That is the correct order — ship the half
that protects before the half that enforces.

## What the review changed

Two reviews ran against PR-D: the repo's async-safety reviewer and a
cross-model (Codex) pass. Between them, three defects landed as fixes.

- **A killed ceremony wedged every page write, permanently.** `preparing`
  refuses all page writes, the lease dies with the process, and `abort_cutover`
  needs one — so SIGINT during the eviction loop left no way out but editing
  `app_metadata` by hand. The daemon now releases a stranded `preparing` fence
  at startup, which is sound because a ceremony and a running daemon are
  mutually exclusive by construction (data-root lock, port probe, service-unit
  check).
- **An ungated page write on the repair path.** `rename_page_title_cas_inner`
  wrote a page's `.md` with no permit. The tooth that should have caught it
  matched the literal `.write_page(`, so `.write_page_with_after_target_write(`
  walked past. The tooth now enumerates the *permitted* forms, so a new
  `write_page_*` variant fails closed.
- **The lease was `Clone` and borrowed, not linear.** Two aliases could both
  pass the fence check, and one could then write its generation after the other
  had already committed and reported success. It is now consumed by value and
  not `Clone`, so the second use does not compile. `a_spent_lease_cannot_commit_again`
  was deleted with it — the compiler is the stronger tooth.

Also: the cutover re-plans *under* the lease rather than before it, closing the
window where a page could flip supported between the plan and the fence.

Two review findings were accepted and **not** fixed, with reasons:

- A crash between the commit and the post-commit reconcile leaves generation 1
  with an unplanned hidden file on disk. The next daemon startup runs
  `enforce_projection_directory_invariant` and evicts it, and the daemon is
  stopped for the whole ceremony anyway, so the exposure window is bounded by a
  restart the operator is already told to perform.
- The permit carries only a page ID, not the fence epoch, so a permit taken
  before `preparing` is still valid after. Binding the epoch would need a DB
  read at write time under the projection lock. Unreachable today for the same
  daemon-stopped reason — which is now a load-bearing invariant in two places
  and should be treated as one.

### A third tooth that was not load-bearing

`a_released_fence_invalidates_the_lease_it_took_back` shipped claiming the epoch
bump was what stopped a released lease from committing. Probing that mutation
came back green: `commit_cutover` compares the whole `(epoch, phase)` tuple and
a lease is always `preparing`, so the phase alone already refuses. The bump
stays for monotonicity; the claim is gone. That is three teeth in this PR that
passed under their own mutation — the probe is earning its cost.

## Review findings, and the two deliberately left open

An adversarial review of the archive change found seven items. Five are fixed in
`64d5b0d2`; the two below are deferred on purpose, and the third is a constraint
on work that has not started yet.

Worth noting where the fixed ones lived: none were on the happy path. The tests
and the live isolated run both exercised a cutover that *succeeded*. Every real
defect was on the failure-and-rerun side — a partial eviction, a stale entry with
no file, a racing `create_dir`. A verify that only drives the success case cannot
see them.

The sharpest one was visible in my own verification output and went unread: the
consent prompt printed `Move 2 file(s)` and then moved 3, because it was fed
`plan.evictions.len()` (pages) for a string that says files. The sync-conflict
twin added in this same PR is exactly what separates the two counts. Reading the
number against the outcome, not just checking the outcome, is the lesson.

### Deferred: the fence is single-use, and says so too late

`swap_cutover_fence` has no `Committed -> Off` transition — `truth_exposure_test.rs`
asserts its absence deliberately, to prevent rollback. The consequence is that a
second forward cutover (`--generation 2 --apply`) passes the generation check,
plans, prints the eviction list, prompts *"Move N file(s) ... (y/N)"*, and only
then fails inside `begin_cutover` with `phase committed`. It asks for consent to
an operation that cannot happen.

Not urgent: generation is 0, so nobody has reached a second cutover. But the fix
is a guard BEFORE the prompt carrying the recovery step, not a new transition —
the rollback protection the test defends is worth keeping, and a forward cutover
cannot walk anything back anyway (`cmd_cutover.rs` already refuses
`generation <= current`).

### Deferred: human_reviewed outranks the machine forever, not per version

`page_truth_state` carries `reviewed_page_version` and `reviewed_page_digest`, and
a CHECK requiring both whenever `human_reviewed = 1`. The schema comment states
the intent plainly: approval is of a specific text, never of a page in
perpetuity. But `visible_at` consults the bare boolean, and `page_truth_states`
does not even SELECT the binding columns — `reviewed_page_version` has no
non-test reader in the tree. So approving a page at version 3 exempts it forever,
including after the refinery rewrites it to version 9.

This OVER-keeps, so it costs no file and is safe to leave. It is listed because
the code currently delivers a weaker guarantee than `truth_contract.rs` claims,
and the gap is the kind that gets discovered by the enforcing half rather than
before it. Closing it means reading both columns and comparing against the
page's current version and digest — design work, not a patch.

### Constraint on the producer that does not exist yet

`evaluated_at` is the column the whole three-state fix rests on, and its meaning
is defined by nothing but a comment. It MUST mean "a judgement concluded and did
not support". No CHECK, no linkage to `claim_derivation_jobs`, nothing enforces
that. A producer that stamps it when a judgement STARTS — or that stamps it for
an in-flight or abandoned derivation — turns every page it touches into
`Unsupported` and archives the vault on the next pass. That is the same shape as
the bug this PR exists to fix, re-entering through the write side.

Whoever builds the promotion path owes this a tooth, not a comment.
