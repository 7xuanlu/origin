## 1. The existing consumer contract

The daemon side is `community-read-v1`
(`crates/wenlan-types/src/communities.rs:6`), carried as `schema_version` on
every list response (`:60`, `:74`, `:82`).

The app validates it on every page of every fetch, as a strict inequality against
that one pinned string.

> **Decision S0-102 — M6 never widens `community-read-v1`.** Every M6 addition
> travels on a new versioned wire with its own constant. Because the app's check
> is a strict equality, *any* change to what `community-read-v1` means —
> including a purely additive one — is indistinguishable to an older app from a
> correct response. Additive-and-safe is a property of the encoding, not of the
> consumer, and this consumer does not have it.

## 2. The readiness state machine

The app models coverage as three statuses and nine failure reasons:

```ts
// wenlan-app@origin/main src/lib/graph/community.ts:22-33
export type CartographyStatus = "ready" | "fallback" | "partial-error";

export type PartialErrorReason =
  | "transport"
  | "old-daemon"
  | "schema-mismatch"
  | "generation-mismatch"
  | "interrupted"
  | "member-count-mismatch"
  | "unknown-community"
  | "conflicting-assignment"
  | "foreign-space";
```

| Reason | Producing condition (app-side) |
|---|---|
| `old-daemon` | HTTP `404` or `405` from the community endpoints |
| `transport` | any other thrown error |
| `schema-mismatch` | `response.schema_version !== COMMUNITY_READ_SCHEMA_VERSION` |
| `foreign-space` | any returned row whose `space` differs from the requested space |
| `interrupted` | pagination hit the `MAX_PAGES` ceiling without `next_cursor === null` |
| `generation-mismatch` | the community summaries do not all share one `published_generation`, or a member's differs from it |
| `unknown-community` | a member names a `community_id` absent from the declared summaries |
| `conflicting-assignment` | one `node_id` maps to two different `community_id`s |
| `member-count-mismatch` | a summary's `member_count` differs from the drained distinct member-set size |

> **Decision S0-103 — M6 adds no new `PartialErrorReason` value and no new
> status.** M6 readiness travels as a separate field (§6) rather than as a tenth
> reason. The nine reasons describe whether the *map* is trustworthy; overloading
> them with genesis readiness would collapse "is this map coherent" and "may I
> create a candidate" into one question, and D14's per-signal independent cutover
> needs them to stay two.

Four of these — `member-count-mismatch`, `unknown-community`,
`conflicting-assignment`, `generation-mismatch` — are cross-row consistency
checks the daemon does not perform on the app's behalf. They are the app
independently re-deriving that the daemon's paginated answer is internally
coherent.

> **Decision S0-104 — the daemon does not retire those checks by promising
> coherence, and PR-A must not optimize them away.** They are the app's only
> defense against a daemon that is correct in each individual response and
> incoherent across a paginated sequence — exactly what a generation bump
> mid-pagination produces. A promise is not a check.

## 3. Space encoding, fallback namespacing, and the no-mixing guarantee

Identities are built from a tag-discriminated per-space segment plus one of three
family prefixes:

```ts
// wenlan-app@origin/main src/lib/graph/cartography.ts:166-178
result.set(
  id,
  communityId !== undefined
    ? `durable:${segment}:${encodeURIComponent(communityId)}`
    : `unassigned:${segment}:${encodeURIComponent(id)}`,
);
// ...
for (const [id, localId] of local) {
  result.set(id, `fallback:${segment}:${encodeURIComponent(localId)}`);
}
```

The segment is `s<encoded space>` for a named space and the bare token `u` for
unscoped. Every component is percent-encoded, so no component can contain an
unescaped `:` — no daemon-controlled string can forge another family's prefix,
and two spaces' local IDs can never compare equal.

**The no-mixing guarantee is structural rather than checked.** The family
decision is made once per space — the loop iterates spaces, and the branch tests
that space's cartography status — so a space is wholly durable or wholly
fallback. There is no per-node branch that could produce a mixed space.

> **Decision S0-105 — M6 keeps the family decision at space granularity and adds
> no fourth family.** An unaccepted M6 candidate is not a new identity family; it
> is a proposal *about* an identity, and it travels on the proposal wire (§5).
> A `candidate:` family would put unaccepted machine output into the same
> namespace as durable assignments, which is the mixing this design forbids.

## 4. The generation and pagination handshake

A space is declared ready only after draining both endpoints and passing every
check in §2. The fields the predicate consumes: `schema_version`, per-row
`space`, `next_cursor`, per-community and per-member `published_generation`,
`community_id`, `member_count`, and `node_id`.

Two properties to pin, because M6 will be tempted to relax both:

> **Decision S0-106 — readiness is all-or-nothing per space, and a space with
> zero durable rows is `fallback`, never `ready`.** An empty durable assignment
> is indistinguishable from "grouping has not run here yet", and reading it as
> ready-but-empty would retire the heuristic on a space that has no map at all.

> **Decision S0-107 — the generation is validated as a single value across the
> whole drained set, not as a monotone bound.** The weaker check — "no member is
> older than the summaries" — accepts a paginated read that straddled a
> republish, which is precisely what `generation-mismatch` exists to catch. M6's
> candidate and frontier reads inherit the stricter rule.

## 5. The new M6 wire

D13: *"Every actionable M6 proposal is typed; unknown variants fail visibly
rather than being silently skipped."*

> **Decision S0-108 — M6 ships one new versioned module,
> `M6_ACTION_SCHEMA_VERSION = "m6-action-v1"`, carrying closed payload enums, all
> `deny_unknown_fields`. `community-v1` is untouched.**
>
> ```rust
> #[serde(tag = "kind", rename_all = "snake_case", deny_unknown_fields)]
> // every variant: `cutover_generation` (uniform, S0-109 fact 1/3)
> //              + its own computation clock (content staleness)
> pub enum M6CandidateCard {
>     EvidenceCluster   { space_id, slot_id, page_id, cutover_generation, group_handles,
>                         group_count, group_kinds, score, coverage_epoch },
>     OrphanWikilink    { space_id, slot_id, page_id, cutover_generation, label_handle,
>                         referring_page_count, coverage_epoch },
>     CommunityOverview { space_id, slot_id, page_id, cutover_generation, community_id,
>                         community_generation },
>     SpaceOverview     { space_id, slot_id, page_id, cutover_generation,
>                         space_overview_generation },
> }
>
> #[serde(tag = "kind", rename_all = "snake_case", deny_unknown_fields)]
> pub enum M6FrontierCard {
>     UnformedTopic     { space_id, cutover_generation, group_handle, group_kind,
>                         coverage_epoch, first_seen_at, group_count },
> }
>
> // artifact 8's OverviewProposalPayload (S0-84) joins this module unchanged.
> ```
>
> Every variant carries `space_id` — D13's per-node rule applied to cards, with
> S0-158's ID-valued field — plus
> **two** clocks, because two different questions are being asked of it:
>
> | Field | Uniform? | Answers |
> |---|---|---|
> | `cutover_generation` | **yes, every variant** | *was this card minted under the current enforcement regime?* — the fact S0-109 gates actions on |
> | the variant's own computation clock | no, differs by variant | *is the card's content stale against its inputs?* |
>
> The per-variant clock is `coverage_epoch` for the two group-derived signals,
> `community_generation` for a community overview, and `space_overview_generation`
> for a space overview.

> **Decision S0-148 *(amended rev 3, round-2 finding 9 — number kept)* — every
> variant carries BOTH clocks, and both are asserted structurally.** Rev 1 shipped
> two variants with no generation at all. Rev 2 fixed that by mandating "exactly
> one generation field per variant" — which round 2 correctly found does not
> discharge S0-109, because the field it mandated is the variant's *computation*
> clock while S0-109 gates on the *cutover* clock. A card carrying a matching
> `coverage_epoch` says nothing about whether the daemon has cut over, so the
> conjunction S0-109 requires could not be evaluated from the card at all.
>
> PR-A's wire test therefore enumerates the variants and asserts two accessors on
> each: `cutover_generation`, whose name and type are identical across variants,
> and the variant's own computation clock. Adding a variant missing either fails
> to compile.

**`M6FrontierCard::UnformedTopic` carried the same leak** and is fixed the same
way: `group_id` becomes `group_handle` + `group_kind` per S0-145. It is worth
naming separately because the frontier card is the one an operator is most
likely to dump while debugging an empty frontier, and a debug dump of raw group
IDs is a corpus dump.

The enums are separate rather than one enum with a category tag because they have
different action verbs (§7) and different staleness keys; merging them would
force every consumer to handle variants it can never act on.

### 5.1 What was removed, and why (finding 1)

The shape above originally read
`EvidenceCluster { space, slot_id, page_id, group_ids, score, coverage_epoch }`
and `OrphanWikilink { space, slot_id, page_id, label, referring_page_ids }`.
Both leaked.

An `independence_group_id` is not an opaque key. It is built by
`base_independence_key` as `format!("src:{s}")` from `source_identity`
(`crates/wenlan-core/src/provenance.rs:171`-`:177`), and `source_identity` is
the source memory's URL or source id (`crates/wenlan-core/src/edge_grounding.rs:519`-`:533`;
artifact 3 §4). A `Vec<String>` of those is a list of the user's source
documents and web addresses in plaintext.

**The exposure is wider than the app.** §7 marks card *reads* as requiring no
presence, deliberately — "HTTP/MCP callers may inspect or suggest". The daemon
binds loopback and is unauthenticated, so every same-user process and every
connected MCP client could have listed cards and harvested source identities
across the whole corpus. That is STOP #10 — *"private corpus data reaches
JavaScript, HTTP/MCP, logs, receipts, public/MCP exports, or committed
evidence"* — reached through the open read, not through the app.

> **Decision S0-145 — a card references a group only by an opaque per-install
> handle, and the handle is not derived from anything a caller can guess.**
>
> `group_handle = truncate(HMAC(card_handle_salt, independence_group_id))`,
> where `card_handle_salt` is generated once per install and stored owner-only,
> **separate from the M5 presence secret** — key separation, so a compromise of
> one is not a compromise of the other, and so rotating card handles does not
> invalidate outstanding capabilities.
>
> A plain digest is not sufficient. `independence_group_id` is low-entropy and
> guessable — an attacker who suspects the user ingested a given URL can hash
> it and test for membership. The salt is what makes handle sets
> non-dictionary-attackable and non-correlatable across installs.
>
> Handles are stable within an install so the app can correlate a group across
> cards and reads, which is the only property the UI actually needs from them.

> **Decision S0-146 *(amended rev 3, round-2 finding 1 — number kept)* — card
> reads are two-tier, and NEITHER tier carries a corpus-derived display string.**
>
> | Tier | Auth | May carry |
> |---|---|---|
> | list | none — open to HTTP/MCP, per D13 | handles, counts, enum kinds, scores, generations, space, IDs the daemon minted |
> | detail | presence capability | additionally, the daemon-minted IDs behind one named card's handles (page IDs, slot IDs) |
>
> **Rev 2 put display strings on the detail tier and that was wrong.** STOP-10
> names *destinations*, not permission levels — *"UI-presence material or private
> corpus data reaches JavaScript, HTTP/MCP, logs, receipts, public/MCP exports, or
> committed evidence"* (`gp@wenlan-app:754`-`:756`). There is no authorized-caller
> clause in it, so a presence capability cannot discharge it; gating the read
> changes who can trigger the leak, not whether corpus text lands in JavaScript.
> Rev 2 reasoned about *access control* where the contract legislates *flow*.
>
> **What replaces it.** Nothing on an M6 surface renders corpus text. Where a
> human needs to see actual content, the affordance is navigation into the
> existing page view — a surface that predates M6, is already the user's
> authorized view of their own content, and gains no new capability here. M6 adds
> counts, kinds and handles; it adds no new path for prose.
>
> This still preserves D13's actual sentence: HTTP and MCP callers can *inspect* —
> they see that a candidate exists, its shape, its score, and how many independent
> groups back it — they simply cannot enumerate the corpus.

**What the UI can still show without the detail read.** The judgement a human
makes on an evidence-cluster card is "are these really independent sources?"
The list projection answers it structurally: `group_count` plus `group_kinds`
(the enum discriminant of each source — document, webpage, chat, capture),
which is schema-level and carries no content. A card reading "3 independent
groups: 2 documents, 1 web page" is actionable; the URLs are one
presence-authorized click away.

> **Decision S0-147 — `referring_page_ids` becomes `referring_page_count` on the
> list tier.** Page IDs are daemon-minted and not themselves corpus content, but
> a list of them is a join key straight into page titles and prose over the same
> open surface, which reconstructs the leak one hop out. The count is what the
> card needs to render; the IDs come with the detail read.

## 6. The readiness handshake before enabling M6 actions

> **Decision S0-109 — enabling any M6 action requires the conjunction of three
> independent facts, and the app computes the conjunction itself.**
>
> 1. **Daemon cutover.** The per-space cutover generation for that signal is
>    greater than 0. At generation 0 the daemon omits the field entirely, so an
>    old daemon and a pre-cutover daemon look identical to the app — correct,
>    since neither can serve the action.
> 2. **Cartography readiness.** That space's `CartographyStatus` is `"ready"`.
> 3. **Card freshness.** The card's `cutover_generation` equals the daemon's
>    current one for that signal — *(rev 3, round-2 finding 9: this is the cutover
>    clock, never the variant's `coverage_epoch` or `community_generation`, which
>    answer a different question and can match while the daemon has not cut
>    over)*. Content staleness is judged separately against the variant's own
>    clock and surfaces as S0-110's typed conflict, not as an action gate.
>
> The app computes it because the daemon cannot: fact 2 is the app's own
> derivation (§2), and a daemon asserting "you may act" would be asserting
> something about a check it never ran.

> **Decision S0-110 — a stale action fails with a typed conflict naming the
> generation it expected, and the app re-fetches rather than retrying.** A bare
> failure leaves the app unable to distinguish "your card is old" from "the
> daemon refused you", and only the first is safely retryable.

## 7. Presence-capability requirements

D13: *"Candidate create/merge/dismiss and overview transfer/retire actions
require the M5 Tauri-owned UI-presence capability plus operation receipt.
HTTP/MCP callers may inspect or suggest; they cannot resolve as human."*

The binding design is `docs/plans/2026-07-27-m5-presence-threat-model.md`, which
is on this branch. A real user gesture reaches the **Tauri Rust backend**
(`:49`-`:50`), which mints a capability HMAC'd with the per-install secret and
bound to action, target IDs, base/revision digests, caller ID, operation ID, a
one-shot nonce, a 60-second expiry, and a protocol version (`:51`-`:62`). **The
backend submits the mutation itself; frontend JavaScript never receives the
capability** (`:64`-`:66`).

| M6 action | Presence required |
|---|---|
| candidate create | yes |
| candidate merge | yes |
| candidate dismiss | yes — see S0-111 |
| overview transfer | yes (artifact 8, S0-76) |
| overview retire | yes (artifact 8, S0-76) |
| inspect / list cards (list tier) | no — reads stay open to HTTP and MCP, and carry no corpus content (S0-146) |
| card detail (daemon-minted IDs behind one card's handles) | **yes** — S0-146; carries no corpus-derived string at any auth level |
| suggest a candidate | no — a suggestion is not a resolution |

> **Decision S0-111 — dismiss requires presence even though it destroys
> nothing.** It is the action most likely to be argued down, because it feels
> like closing a notification. It is not: a dismissal writes a suppression that
> stops the same card being re-proposed (artifact 5 §4), so an unauthenticated
> dismiss is a way to silence the review surface without a human ever seeing it.

**Ordering is fixed and non-obvious** (threat model `:70`-`:90`): receipt
replay/collision lookup runs **first**, before capability validation and nonce
consumption. Same caller + operation + request digest replays the stored response
without re-consuming the nonce; same caller + operation with a different digest
is a conflict that writes nothing; a new operation validates, consumes the nonce
inside the mutation transaction, and executes.

> **Decision S0-112 — every M6 action reuses that ordering and the existing
> nonce table verbatim; M6 adds no second presence path.** The threat model's
> reasoning (`:88`-`:90`) — validating first burns the nonce on the retry of an
> already-applied mutation, turning an idempotent retry into a hard failure — is
> not specific to M5's actions and applies unchanged.

**Refusals are deliberately coarse** (threat model `:138`-`:141`):
`presence_invalid`, `presence_expired`, `presence_replayed`, `presence_conflict`.
They never echo the submitted capability and never distinguish "bad HMAC" from
"unknown nonce" in a way that would let a caller probe the secret byte by byte.

The redaction contract (`:127`-`:136`) is absolute: the HMAC, the raw capability,
the install secret, and the raw nonce are never logged, exported, serialized into
receipts, or returned in errors. The immutable `attests` payload may carry only
protocol version, nonce **digest**, verification time, viewed page version,
revision digest, and caller/operation identity.

> **Decision S0-158 *(rev 4, round-3 N2; regrounded rev 5, round-4 item 1)* — the
> field is named `space_id` and carries `spaces.id`, the daemon-minted UUID. This
> is a NEW boundary rule, not a description of what the columns hold today.**
> S0-113 forbids any user-authored string, and a Space carries both:
> `Space { id, name }` (`crates/wenlan-types/src/memory.rs:350`-`:352`), where
> `name` comes straight from the caller (`CreateSpaceRequest { name }`,
> `crates/wenlan-types/src/requests.rs:253`-`:255`) and `id` is minted by the
> daemon as `uuid::Uuid::new_v4()` (`crates/wenlan-core/src/db.rs:19190`).
>
> **Rev 4 claimed this was "a clarification, not a change." That was false, and
> the correction matters because PR-A was being told no work was required.** The
> scope columns store the **name**, and three paths show it:
>
> - Renaming a space cascades the **new name** into `memories.space` and
>   `entities.space` (`crates/wenlan-core/src/db.rs:19266`-`:19281`). A column
>   holding IDs would need no cascade at all — that cascade exists *because* the
>   stored value is the mutable name.
> - The ingest write path takes an incoming `space_id`, resolves it with
>   `SELECT name FROM spaces WHERE id = ?1` (`db.rs:21067`-`:21071`), and stores
>   the resulting **name** into `doc.space` and `row.space`
>   (`db.rs:21115`-`:21123`).
> - Space lookup throughout the DB API is keyed by name, not id
>   (`db.rs:19338`, `:19608`, `:19646`); `SELECT id FROM spaces` appears nowhere
>   in the crate.
>
> Rev 4's evidence was the `UNFILED_SPACE_ID` sentinel being a UUID stored in the
> column. It proves nothing: the sentinel row's `id` **and** `name` are
> deliberately the same UUID string, so that a user's own space named "unfiled"
> cannot collide with it on the name-unique constraint
> (`crates/wenlan-core/src/db.rs:688`-`:696`). A name-valued column holds that
> sentinel exactly as well as an ID-valued one.
>
> **The conversion seam PR-A must build.** One direction already exists and is
> reused; the other does not exist and is new work:
>
> | Direction | Where | Status |
> |---|---|---|
> | ID → name, on write | `ResolvedWriteSpace { space_id, space_name, source }` (`crates/wenlan-core/src/space_context.rs:6`-`:10`), resolved at `db.rs:21067` and applied at `db.rs:21115` | exists; M6 writes reuse it unchanged |
> | name → ID, on read | nothing today — no `SELECT id FROM spaces` exists | **new in PR-A**: minting a card from a stored row must resolve the row's name-valued `space` to `spaces.id` before the card leaves the daemon |
>
> The conversion happens **daemon-side, at the wire boundary, in both
> directions** — a card is minted with `space_id`, an action request arrives with
> `space_id`, and no name-valued string crosses into JavaScript in either case.
> Existing rows keep their name-valued columns; M6 does not migrate them, because
> the name→ID resolution is a lookup, not a rewrite.
>
> **An exception for a name-valued `space` was the alternative and is rejected.**
> An exception has to be re-justified by every future reader of S0-113, and it
> would be the only hole in a prohibition whose whole value is being absolute.
> The ID rule also buys a property the name cannot give: a card minted with
> `space_id` survives a rename, whereas a name-valued card silently refers to
> nothing the moment the cascade at `db.rs:19266` runs.

> **Decision S0-161 *(rev 5, round-4 item 1)* — the name→ID resolution is
> fail-closed, and `slot_id`'s space part does NOT change.** Regrounding S0-158
> surfaced a divergence the contract has to settle, because two different space
> values are now in play at once.
>
> `update_space`'s rename cascade touches `memories`, `entities`, and
> `pages`/`workspace` — and nothing else (`crates/wenlan-core/src/db.rs:19266`-
> `:19298`). `communities.space` and `community_members.space` are not cascaded,
> and those are exactly the columns S0-31 digests into `slot_id` (artifact 4 §3.1;
> `db.rs:10448`, `:10460`). So after a rename, a community row still names the old
> space while the `spaces` row carries the new name.
>
> Two rules follow, and they pull in opposite directions on purpose:
>
> 1. **`slot_id` keeps digesting the raw stored string, unchanged.** Switching its
>    space part to `spaces.id` would re-key every existing slot in one release —
>    every card orphaned, every lease stranded — to fix a rename case. S0-31
>    stands as written.
> 2. **Minting a card resolves that stored string to `spaces.id`, and a
>    resolution miss refuses the card.** A stored string naming no live space is
>    the observable form of the non-cascade above. The card is not minted with a
>    placeholder, an empty `space_id`, or the raw string; it is not minted. Silence
>    is correct here because the alternative leaks the name S0-113 forbids, and a
>    card the user cannot act on is worse than a card that is absent.
>
> The consequence is stated rather than hidden: **community-derived cards for a
> renamed space stop appearing until the community rows are re-derived.** That is
> a real behavioural gap, it is bounded to renamed spaces, and it is the honest
> read of a substrate whose cascade does not cover the columns M6 keys on. PR-A
> asserts the refusal; whether the cascade should be widened is a substrate
> question outside Stage 0's scope.

> **Decision S0-113 *(amended rev 3, round-2 finding 1 — number kept)* — M6 card
> payloads are held to the redaction contract as strictly as receipts, because a
> card is the one M6 artifact that reaches the UI.** An M6 card may not carry page
> prose, root identities, prompts, **or any user-authored string** (S0-158 names
> the one field that looks like a counterexample and is not). Rev 1 let
> `M6CandidateCard::OrphanWikilink` carry `label` on the grounds that the card is
> unreadable without it. That was the leak finding 1 named: a wikilink label is
> user-authored text, and no amount of normalizing makes it not corpus content.
> The struct now carries `label_handle` only (§5).

> **Decision S0-114 *(amended rev 3 — number kept)* — D8 normalization still runs,
> but on the daemon side only, as the input to the handle digest.** Artifact 4 §6's
> pipeline rejects control and bidi scalars and caps at 128 scalars; normalizing
> before digesting is what makes the handle stable across trivially different
> spellings of the same link. The normalized string is never serialized. Rev 1
> shipped it to the client and called the normalization a safeguard; normalization
> bounds what the string can *contain*, not where it may *go*.

> **How an orphan-wikilink card stays readable without its label.** The judgement
> the card asks for is *"should this become a page?"*, and the evidence for it is
> the linking context, not the token: the card shows how many pages link to a
> missing target (`referring_page_count`) and offers navigation to those pages,
> where the human reads the wikilink in situ through the existing page view. That
> is strictly more information than a bare label, and it moves no corpus text onto
> an M6 surface.

### 7.1 The exact action wire (finding 9)

The presence *requirements* above said who may act; they did not say what an
action looks like on the wire. Naming it is what makes G10's "typed
daemon/Tauri/TypeScript round-trip" testable rather than aspirational.

**Request** — one shape for all five mutating actions:

```rust
#[serde(deny_unknown_fields)]
pub struct M6ActionRequest {
    pub schema_version: String,   // must equal M6_ACTION_SCHEMA_VERSION
    pub action: M6Action,         // closed enum: candidate_create | candidate_merge
                                  // | candidate_dismiss | overview_transfer
                                  // | overview_retire
    pub space_id: String,         // spaces.id — NOT the name-valued storage
                                  // column; see S0-158's conversion seam
    pub slot_id: String,          // the card's identity
    // BOTH clocks the card carried, discriminated (S0-159). One field could not
    // say which race it lost.
    pub observed_cutover_generation: i64,
    pub observed_content_generation: i64,
    pub operation_id: String,     // idempotency key (M5 receipt lookup)
    pub capability: String,       // minted by the Tauri backend, never seen by JS
}
```

**Response** — a closed three-way enum, because the three outcomes need
different handling and a bare `Result` collapses two of them:

```rust
#[serde(tag = "outcome", rename_all = "snake_case", deny_unknown_fields)]
pub enum M6ActionResponse {
    Applied  { receipt_id: String, new_content_generation: i64 },
    Conflict { clock: M6Clock, expected_generation: i64, current_generation: i64 },
    Refused  { code: PresenceRefusal },   // the four coarse codes, §7
}

#[serde(rename_all = "snake_case", deny_unknown_fields)]
pub enum M6Clock { Cutover, Content }
```

> **Decision S0-159 *(rev 4, round-3 N3)* — every actionable M6 payload carries
> both clocks, and a conflict names which one it lost.** S0-148 gave the cards two
> clocks but rev 3 stopped there: `M6ActionRequest` still sent one
> `observed_generation` and `Conflict` returned one unqualified expected/current
> pair, so exactly the discrimination S0-148 introduced was thrown away at the
> wire. A daemon receiving one number cannot tell a cutover race from a
> content-staleness race, and a client receiving one pair cannot tell the human
> which happened — one is "the daemon changed regime, re-read", the other is "your
> card is stale, refresh". Collapsing them makes one of the two races
> unevaluable, which is the defect S0-148 existed to prevent.
>
> PR-A's structural test asserts three things: the request carries both observed
> generations, `Conflict` carries a `clock` discriminant, and `M6Clock` is closed.
> `OverviewProposalPayload` carries both for the same reason (artifact 8, S0-84).

> **Decision S0-149 *(amended rev 5, round-4 item 3)* — BOTH observed clocks are
> carried in the request and compared server-side; the client never decides
> freshness.** S0-109 has the app compute whether an action may be *offered*; this
> is the different question of whether it may be *applied*, and only the daemon
> can answer it without a race. A client that checked freshness and then sent an
> unconditional mutation would re-open exactly the window S0-110's typed conflict
> exists to close.
>
> The normative form is two fields, `observed_cutover_generation` and
> `observed_content_generation`, and the daemon compares **both**. Rev 4 amended
> the struct and the summary to two clocks but left this body saying
> `observed_generation`, so the artifact's own normative sentence contradicted its
> wire.
>
> **Simultaneous mismatch resolves cutover-first, and `Conflict` reports the
> cutover clock alone.** This is not a tie-break for convenience: a cutover
> mismatch means the daemon changed regime, and the content generation the client
> observed was minted under the *previous* regime, so the content comparison is
> not merely also-failing — it is meaningless. Reporting content staleness in
> that state would send the user to "refresh this card" when the only correct
> remedy is "re-read; the daemon moved". Encoding both conflicts would present two
> remedies of which one is wrong. When the cutover clocks agree and only the
> content clocks differ, `Conflict` reports `M6Clock::Content` as usual. PR-A's
> structural test covers all three mismatch shapes — cutover only, content only,
> and both — asserting the third returns `M6Clock::Cutover`.
>
> `Applied` returns `new_content_generation`, not a bare `new_generation`: the
> cutover clock is not something an action advances, so an unqualified name here
> would be the same collapse on the response side that rev 4 fixed on the request
> side.

> **Decision S0-150 — the round trip is asserted end-to-end in one test, not
> three.** G10 asks for a typed daemon/Tauri/TypeScript round-trip. Three
> per-layer tests all pass while the layers disagree with each other — which is
> the failure mode artifact 10's F3 found already shipped, where the Tauri
> mirror silently drops a field the daemon sends. The test constructs each
> response variant at the daemon, drives it through the real Tauri command, and
> asserts the TypeScript-visible object still discriminates correctly.

**Receipt.** An applied action writes one M5 operation receipt whose `attests`
payload is bound by the redaction contract (S0-113) and carries only: protocol
version, nonce digest, verification time, viewed page version, revision digest,
caller/operation identity, plus the M6 fields artifact 11's F4 flagged as
needing deliberate allowlisting — `slot_id`, `page_id`, `community_id`, and the
card generation. **No group handle, no display string, no label.** A handle is
per-install salted and therefore useless in a receipt, and including one would
put derived corpus identity into an immutable row.

## 8. The unknown-variant rule

This is where D13 and the shipped app disagree, and the disagreement is explicit
in the app's own source. Its community wire types are documented as deliberately
tolerant:

> *"Read-tolerant (no `deny_unknown_fields`): any future additions are ignored
> rather than rejected."* — `wenlan-app@origin/main app/src/api.rs:234-243`

None of `CommunityScope`, `CommunitySummary`, `CommunityListResponse`,
`CommunityMember`, or `CommunityMembersResponse` carries `deny_unknown_fields`,
so unknown fields on that wire are dropped by serde's default.

**This is a deliberate per-wire choice, not a blanket posture, and the precedent
is the strongest argument for S0-115.** The same file marks five structs
`deny_unknown_fields` — `DistillReviewResponse`, `DistillPendingCluster`,
`DistillStalePage`, `DistillOrphanTopic`, `PageRedistillResponse`
(`wenlan-app@origin/main app/src/api.rs:176`, `:188`, `:203`, `:215`, `:222`) —
and those five are exactly the app's *actionable review* wire. So the app already
draws D13's line in the place D13 draws it: strict where a human acts on the
payload, tolerant where the app only reads. M6 is not introducing a new
discipline; it is inheriting an existing one.

On the TypeScript side there is no runtime validation of either wire. There is no
schema-validation dependency in `package.json`, and the community calls do not
even carry a generic:

```ts
// wenlan-app@origin/main src/lib/tauri.ts:2738-2744
export async function listCommunities(
  space: string,
  cursor?: string | null,
  limit?: number,
): Promise<CommunityListResponse> {
  return invoke("list_communities", { space, cursor: cursor ?? null, limit: limit ?? null });
}
```

The declared return type is an unchecked assertion about a payload that crossed a
process boundary. The only runtime checks on that data are the `schema_version`
equality and the per-row `space` check.

> **Decision S0-115 — tolerance is a per-wire property, and the M6 action wire is
> strict on both sides of the Tauri boundary.**
>
> | Wire | Rust posture | TS posture |
> |---|---|---|
> | `community-read-v1` (read) | tolerant, unchanged | unchanged |
> | `m6-action-v1` (actionable) | `deny_unknown_fields` on every payload enum | explicit variant switch whose default **renders a visible unsupported-card state** |
>
> "Fail visibly" needs a concrete definition, because every weaker reading passes
> a naive test. An unknown variant must (a) still render a card in the list
> rather than vanishing from it, (b) show an "unsupported — update the app" state
> in the current locale, and (c) offer no action buttons. Dropping the card is
> the forbidden behavior, and dropping it is exactly what a `filter`-based
> renderer does by default.

> **Decision S0-116 — the TS layer gets runtime variant validation for the
> action wire.** Today's typing is weaker than generics-only: `listCommunities`
> declares `Promise<CommunityListResponse>` over a bare untyped `invoke`
> (`wenlan-app@origin/main src/lib/tauri.ts:2743`), so the return type is an
> assertion the compiler accepts and nothing ever checks. Without a runtime check
> on the action wire, S0-115's exhaustive switch is checked against a type the
> data is merely assumed to have, and an unknown variant arrives as a
> silently-wrong object instead of reaching the default branch. The requirement is
> narrow — validate the `kind` discriminant against the known set before the
> switch — not a whole-payload schema library.

## 9. Three-locale rendering, as a testable enumeration

```ts
// wenlan-app@origin/main src/i18n/resources.ts:1
export const supportedAppLocales = ["en", "zh-Hans", "zh-Hant"] as const;
```

Missing keys fall back to English (`fallbackLng: "en"`), and a key absent from
English too renders as the raw key string — i18next's stock behavior, with no
custom missing-key handler configured. The real guard is a build-time parity test
asserting all three catalogs have identical flattened key sets.

> **Decision S0-117 — D13's three-locale requirement is discharged by
> enumerating the M6 rendered states and asserting that enumeration, not by
> asserting catalog parity.** The parity test already prevents a *missing* key;
> what it cannot prevent is a state that was never given a key at all.
>
> | # | State |
> |---|---|
> | 1–4 | candidate card, one per variant |
> | 5 | frontier card, unformed topic |
> | 6 | overview transfer proposal |
> | 7 | overview retire proposal |
> | 8 | unsupported/unknown variant (S0-115) |
> | 9 | stale card, refresh required (S0-110) |
> | 10 | action disabled — space not ready |
> | 11 | action disabled — daemon not cut over |
> | 12 | action refused — presence (one string; S0-118) |
> | 13 | action succeeded |
>
> Thirteen states, each asserted present and non-empty in all three locales.

> **Decision S0-118 — the four presence refusal codes render as ONE user-facing
> string.** The threat model makes the codes coarse precisely so a caller cannot
> probe the secret (`:138`-`:141`); rendering four distinguishable messages would
> rebuild that oracle in the UI. The distinct codes stay in the typed response,
> for logs and tests.

## 10. Findings

**F1 — the app already draws D13's strict/tolerant line correctly, but draws it
by convention, and the Rust half of it is the only half that exists.** Five
actionable structs are `deny_unknown_fields`
(`wenlan-app@origin/main app/src/api.rs:176`, `:188`, `:203`, `:215`, `:222`)
while the community read wire is deliberately tolerant (`:234-243`). That is
exactly S0-115's rule, shipped. Two gaps remain. First, it is a habit rather than
a mechanism: a new M6 response struct added beside the existing ones is tolerant
by serde's default, and nothing fails if the author does not think about it —
S0-108's separate module is what makes the choice conscious. Second, the
TypeScript half has no equivalent at all; strictness stops at the Tauri boundary,
which is precisely where D13's "fail visibly" has to hold, since the renderer is
what would silently drop the card. This finding downgrades my earlier reading of
the app as uniformly tolerant — it is not, and the discipline M6 needs is already
half-built.

**F2 — no proposal-card UI exists in the app at all.** Searching the app for
`community_split` / `community_merge` / `community_rename` / `CommunityProposal*`
/ `list_community_proposals` returns zero hits in any TypeScript or Rust file,
even though the daemon shipped the full wire
(`crates/wenlan-types/src/communities.rs:96`-`:121`, `:180`-`:203`) and writes
proposals into `refinement_queue`
(`crates/wenlan-core/src/db.rs:14090`-`:14092`). The app's existing
refinement-review surface is for distillation and is not this. So G10's
"actionable proposal cards" clause has **no substrate to test against**, and the
App PR is bigger than "add M6 cards" — it is "build the proposal surface, then
add M6 cards to it." Worth knowing before that PR is sized.

**F3 — the Tauri layer is a hand-mirrored wire that drops any field it does not
declare, so an additive daemon field is a two-repo change, not a one-repo
change.** This is the correction of something I initially read as an oversight.
The app mirrors `scope` as a loose `{ kind: String, name: String }` pair rather
than the real tag-discriminated enum
(`wenlan-app@origin/main app/src/api.rs:245-249`), carries it as
`Option<CommunityScope>` with `#[serde(default)]` (`:266`, `:291`), and no
`.ts`/`.tsx` file reads it — but that is not neglect. The mirror is documented
(`:240-243`) and defended by its own test: *"The daemon's `scope` must survive the
round trip — the Tauri command re-serializes this struct verbatim for the
frontend, so a field the struct doesn't carry is silently dropped, not merely
unread"* (`:2566-2575`), paired with a test that an older daemon omitting `scope`
still parses (`:2584-2603`).

The consequence for M6 is the finding. Because the Tauri structs are hand-written
mirrors rather than a shared crate — the app pins `wenlan-types` 0.14.1, which
predates the communities module (`:235-237`) — **tolerance on the daemon side buys
nothing on its own.** A field added to an M6 response is invisible to the frontend
until the app's mirror declares it, so any M6 wire addition must be planned as a
coordinated change across both repos, and the daemon must never assume the app
can see a field it has not been taught. Reported, not resolved: the clean fix is
for the app to consume the real `wenlan-types` module, which is app-repo work
outside Stage 0's scope.

**F4 — the `attests` payload's allowed-field list has no M6 analogue yet.** The
threat model enumerates exactly what an attestation may carry
(`docs/plans/2026-07-27-m5-presence-threat-model.md:134`-`:136`). M6 adds five
presence-requiring actions (§7) whose receipts will carry M6-shaped fields —
`slot_id`, `page_id`, `community_id`, card generation — none of which are in that
enumeration. It is an allowlist, so the omission fails closed rather than
leaking, but **PR-A must extend it deliberately rather than discovering it as a
test failure**, and each added field needs the same argument the existing six
have: not prose, not a root identity, not capability material.
